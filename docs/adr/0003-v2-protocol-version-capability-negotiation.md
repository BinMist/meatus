# ADR 0003：v2 协议版本与能力位协商

- 状态：已接受（E1-01）
- 日期：2026-11-21
- 决策者：项目负责人

## 背景

MEATUS/1 只用 `Hello.protocol_version = 1` 表示版本，`caps` 实际承担了能力声明：早期客户端用它声明代理类型和 `probe` 诊断能力。V1.4 要加入连接池、QUIC、多入口、IPv6、流元数据和优雅 drain，必须先把版本与能力位的语义定死，否则后续功能会各自解释 `protocol_version`，破坏 1.2.1 / 1.3.0 客户端兼容。

本 ADR 只定稿协商规则与取值；`Welcome` 回显字段属于 E1-02，客户端失败回落属于 E1-04。

## 决策

### 1. 版本取值与语义

- MEATUS/1 的版本值为 `1`，MEATUS/2 的版本值为 `2`。
- `Hello.protocol_version` 表示**客户端支持的最高主版本**，不是“请求强制使用的版本”。
- 服务端声明支持区间 `[1, 2]`；在区间内选择双方都支持的最高版本，即 `min(client_version, server_max_version)`。
- 版本只表达**不兼容的主版本**。v2 内的新字段、新消息、新能力都靠 `caps` 开关；不为加法改动提升主版本。
- 不支持次版本号、补丁版本号或每消息版本号。

### 2. 协商顺序

服务端按以下顺序处理，任一步失败即终止：

1. 读取首帧，必须是 `Hello`；不是则按协议错误断开。
2. 校验 `protocol_version` 是否落在服务端 `[1, 2]` 区间；不在区间返回 `ErrorCode::UnsupportedVersion (1002)`，`fatal = true`，消息包含服务端支持区间。
3. 选版本：v1 客户端选 `1`；v2 客户端选 `2`。
4. 过滤 `caps`：只保留注册表内、且 `since <= 选定版本` 的能力；未知或当前版本不支持的能力进入 `ignored_caps`。
5. 校验 `client_id` / `tenant_id` 非空，再发 `Challenge`。
6. 完成 HMAC 认证后发 `Welcome`；E1-02 在 `Welcome` 中加法回显 `protocol_version` 与实际接受的 `caps`。
7. 把**过滤后的 caps**写入客户端状态，后续 `Probe` 等能力判断只看过滤结果。

版本协商先于身份校验，保证旧版本错误能在认证前明确返回；但失败仍走统一的 3 秒握手延迟，避免被用于快速枚举。

### 3. 能力位规则

- `caps` 是大小写敏感的 ASCII token；首尾空白会被去掉，空 token 丢弃。
- 重复 token 只保留第一次出现；接受列表保持客户端声明顺序，便于日志比对。
- 未知 token **不失败**，只记录到 `ignored_caps`；服务端不得因为客户端多声明能力而拒绝握手。
- 已知但 `since` 高于选定版本的能力同样忽略，例如 v1 会话中的 `quic`。
- 缺失能力等于“不支持该功能”，功能保持关闭；没有“必需能力”概念。
- 能力名一旦发布不复用、不改语义。删除能力需要提升主版本；新增能力优先在现有主版本内追加，默认关闭并由旧端忽略。

当前注册表：

| 能力 | since | 声明方 | 语义 |
|---|---|---|---|
| `tcp` | 1 | 客户端 | TCP 代理 |
| `udp` | 1 | 客户端 | UDP 代理 |
| `http` | 1 | 客户端 | HTTP 代理 |
| `https` | 1 | 客户端 | HTTPS 代理 |
| `socks5` | 1 | 客户端 | SOCKS5 代理 |
| `probe` | 1 | 客户端 | 接受服务端诊断 `Probe` |
| `stream_meta` | 2 | 双方 | 数据流携带 `trace_id` / `connection_id` |
| `drain` | 2 | 双方 | 优雅 drain |
| `conn_pool` | 2 | 客户端 | 连接池 |
| `quic` | 2 | 双方 | QUIC 传输 |
| `multi_addr` | 2 | 客户端 | 多入口地址 |
| `ipv6` | 2 | 双方 | IPv6 监听与拨号 |

`caps` 只表示“实现了该能力”，不表示“本次连接已启用”。是否启用仍由配置决定，例如 QUIC 默认关闭、连接池默认关闭。

### 4. 失败与回退

- 客户端版本低于 `1` 或高于 `2`：服务端返回 `1002`，不进入认证。
- 1.4 客户端连接 1.3 服务端：1.3 服务端只接受 v1，会返回 `1002`；E1-04 实现客户端收到 `1002` 后以 `protocol_version = 1` 重连一次并记住回落结果。回落前不得发送任何 v2 专属字段。
- v2 协商成功但某能力缺失：不重试、不降版本，直接关闭对应功能并记录原因。
- v1 客户端连接 1.4 服务端：正常握手，服务端不得发送 v2 专属帧；`Probe` 仍只发给声明 `probe` 的客户端。

### 5. 兼容矩阵

| 客户端 | 服务端 | 结果 |
|---|---|---|
| 1.2.1 / 1.3.0（v1） | 1.4.0（v2） | v1 握手成功，v2 能力全部忽略 |
| 1.4.0（v2） | 1.4.0（v2） | v2 握手成功，按交集启用能力 |
| 1.4.0（v2） | 1.3.0（v1） | E1-04 前返回 1002；E1-04 后客户端回落 v1 |
| 任意 v3+ | 1.4.0（v2） | 返回 1002，不猜测未来版本 |

## 代价

- 能力位是字符串而非枚举，拼写错误只能进入 `ignored_caps`，不会在协议层报错；需要靠注册表和日志发现。
- 版本字段只有主版本，无法表达“v2.1 的中间状态”；所有加法能力必须能独立关闭。
- `Welcome` 未回显前，客户端只能确认自己请求的版本，不能确认服务端最终选择；E1-02 必须补齐该字段。
- E1-04 完成前，1.4 开发客户端不能连接 1.3 生产服务端；这是 M1 内部的临时限制，不进入发布门禁。

## 备选方案

| 方案 | 放弃原因 |
|---|---|
| 每个消息带版本号 | 帧开销与实现复杂度高，且无法解决首帧前的行为差异 |
| 未知能力直接拒绝 | 旧服务端遇到新客户端会全面断连，违背“只做加法” |
| 客户端强制指定版本 | 服务端无法在同一次握手内选择交集，只能反复重试 |
| 用 protobuf 字段存在性代替能力位 | 无法表达“实现了但本次关闭”，也不便于配置与日志 |

## 落地

- 注册表与协商函数在 `crates/meatus-proto/src/negotiation.rs`。
- 服务端在 `crates/meatus-server/src/control.rs` 的 `run_session` 调用 `negotiate`，只把过滤后的 caps 写入状态和 `Probe` 判断。
- 客户端 Hello 使用 `default_client_caps()`；当前只声明已实现的 v1 能力，协议版本为 `2`。
- 单测覆盖：v1 客户端、v2 客户端、v1 服务端拒绝 v2、未知版本、未知能力、空/重复/带空白能力、v2 能力在 v1 会话被忽略。
