## 3. 目标与非目标

### 3.1 目标

1. **Relay 组**：两台 relay 共享 group 身份、签名配置包和端口段，配置不一致拒绝启动；
2. **HTTP/HTTPS 双活**：两台 relay 同时监听 80/443，同一域名多 A，单台故障时新请求切到存活节点；
3. **TCP/UDP 主备**：客户端同时向主备 relay 注册，主 relay 故障后新连接可从备 relay 对应端口进入；
4. **证书同步**：只由 primary 续期，secondary 在 5 分钟内加载新证书，禁止双签发；
5. **健康与摘除**：relay 健康、配置漂移、证书指纹可观测；不健康节点自动从面板轮转中摘除；
6. **滚动升级**：复用 1.4 drain，支持逐台 drain、升级、回滚，新连接失败数为 0；
7. **传输加固**：修复 QUIC 控制面饥饿；对连接池默认化给出数据结论，不无证据改默认；
8. **跨平台**：Windows 服务与托盘、macOS 菜单栏与公证、Linux deb/rpm、签名自动更新、桌面 GUI。

### 3.2 非目标（本版不做）

- 不做 3 台以上 relay 的 Raft / etcd / 自动选主；V1.5 固定 primary / secondary 静态角色；
- 不做 TCP/UDP 在途会话迁移；主 relay 挂掉时，已建立连接允许失败，只保证新连接可恢复；
- 不做全局端口分配器；沿用每 relay 独立端口段，端口段不得重叠；
- 不做 Kubernetes Operator、Anycast、多地域选路；
- 不做 OIDC / SSO、插件系统、Helm / Terraform；
- 不做 Windows Server 服务端；Windows 只交付客户端；
- 不把单机生产伪装成 HA；没有第二台 relay 时，`1.5.0` 只以 standalone 模式上线。

## 4. 兼容性契约

| 契约 | 要求 |
| --- | --- |
| 旧服务端 | 1.2.1 / 1.3.0 / 1.4.0 客户端继续可接入 1.5.0 standalone |
| 旧客户端 | 1.5.0 relay 组在未启用 `[relay]` 时行为与 1.4.0 一致 |
| 协议 | 继续 `MEATUS/2` 加法字段；`Hello` / `Welcome` 只增 tag，不删不改旧 tag |
| 配置 | `[relay]` 可缺省；缺省即 standalone；新增字段均有默认值 |
| 客户端 | `server_addrs` 原语义保留；新增 `[client.relay]` 仅显式启用 multi-home |
| 端口 | 每 relay 的 `ports.range` 独立；同组端口段重叠时 bundle 校验失败 |
| 数据 | 不引入数据库；现有 `/data` 配置、审计、ACME 缓存继续可读 |
| 回滚 | 1.5.0 配置去掉 `[relay]` 后可回退 1.4.0；证书与数据备份独立保留 |

拟新增协议字段（G1-01 冻结）：

- `Hello.relay_group`：客户端声明的 relay 组；空表示 standalone；
- `Hello.relay_id`：客户端当前连接的 relay id，仅诊断；
- `Welcome.relay_group` / `Welcome.relay_id` / `Welcome.relay_role`：服务端回显；
- `Welcome.group_epoch`：配置包版本，客户端据此判断是否需要重载成员列表。

## 5. 拟定配置契约

### 5.1 服务端

```toml
[relay]
id = "relay-a"
group = "prod"
role = "primary"                  # primary | secondary
advertise_addr = "relay-a.example.com:7000"
bundle = "/etc/meatus/relay-bundle.json"
bundle_pubkey = "ed25519:BASE64"  # 离线私钥签名，节点只持公钥
health_bind = "127.0.0.1:7401"
health_interval_s = 5
peer_timeout_s = 5
peer_secret_file = "/etc/meatus/relay-peer.key"  # 32B，0600，用于 peer HMAC
cert_sync = "push"                # off | push | pull
```

约束：

- `[relay]` 缺省时完全保持 1.4 standalone 行为；
- `id` 在组内唯一，`group` 非空，`advertise_addr` 必须是可被对端访问的控制地址；
- `role = "primary"` 才允许 ACME 下单；secondary 只读证书缓存；
- `peer_secret_file` 不得与 `admin_token`、DNS token 混用；
- `health_bind` 只绑定 loopback 或私网，不暴露公网。

### 5.2 签名配置包

`meatus relay bundle export` 生成 JSON，至少包含：

```json
{
  "version": 1,
  "group": "prod",
  "epoch": 3,
  "generated_at": "2026-11-23T00:00:00Z",
  "relays": [
    {
      "id": "relay-a",
      "role": "primary",
      "control_addr": "relay-a.example.com:7000",
      "http_domains": ["*.example.com"],
      "ports": [20000, 20999]
    },
    {
      "id": "relay-b",
      "role": "secondary",
      "control_addr": "relay-b.example.com:7000",
      "http_domains": ["*.example.com"],
      "ports": [21000, 21999]
    }
  ],
  "config_hash": "sha256:...",
  "signature": "ed25519:..."
}
```

校验规则：

- `version` 必须为 `1`；`group` 与 `relay.group` 一致；`relays` 恰好 2 个且恰好 1 个 `primary`；成员 `id` 组内唯一；
- `ports` 是闭区间 `[start,end]`，要求 `start >= 1024 && start <= end`，两段严格不重叠（`next.start > prev.end`）；
- `config_hash` 是除 `config_hash` / `signature` 外 body 的 canonical JSON SHA-256；签名对象是这个 `sha256:` 字符串，不是 body 原始 JSON；
- 启动时验签失败、`group` 不匹配、端口段重叠、`config_hash` 不匹配、`epoch` 回退，任一命中即拒绝启动；
- bundle 只包含可公开的组拓扑，不包含 token、私钥、DNS API token；私钥只在签名机保存，不下发 relay 节点；
- 证书同步只传证书链、私钥和账户缓存，使用 group HMAC 鉴权，不落日志。

### 5.3 客户端

```toml
[client]
server_addrs = ["relay-a.example.com:7000", "relay-b.example.com:7000"]

[client.relay]
group = "prod"
multi_home = true
health_interval_s = 5
```

约束：

- `multi_home = false` 时按 1.4 的顺序切换语义，不建立第二条控制连接；
- `multi_home = true` 时对每个成员保持控制连接，proxy 注册到所有成员；
- 每个成员返回自己的 `ProxyOk.remote_port`，客户端保存 `name -> {relay_id, port}` 映射；
- 任一成员注册失败不阻断其他成员；面板显示 `registered / degraded / failed`。

## 9. 验收与门禁

### 9.1 HA 功能验收

| 场景 | 通过标准 |
| --- | --- |
| Standalone 回归 | 不配 `[relay]` 时，1.2.1 / 1.3.0 / 1.4.0 客户端行为与 1.4.0 一致 |
| HTTP 双活 | DNS 双 A；停一台 relay，1 小时连续探测 0 个 5xx，最大中断 <3s |
| 证书同步 | staging 证书续期后，secondary 在 5 分钟内加载；两节点指纹一致；无重复下单 |
| 配置漂移 | 改动 secondary 配置 hash 或 bundle epoch 回退，启动被拒绝；面板告警 |
| TCP 主备 | 客户端注册两成员；停 primary 后 5s 内 secondary 新连接成功；在途连接失败不判回归 |
| UDP 主备 | 同上；会话不迁移，新会话从备端口进入 |
| 滚动升级 | 逐台 drain + 升级 + 回滚；1000 个新请求 0 失败；单台回滚 <10 分钟 |
| 混沌 | kill -9 primary、30s 网络分区、证书文件只读、bundle 损坏，逐项有预期结果 |
| QUIC | 32×16KB×10s 跑 10 轮，成功率 ≥95%；控制 Pong 不超时；未达标则 `auto` 不默认 |
| 连接池 | 产出默认化评估报告；没有“默认开启”结论就不改默认 |

### 9.3 质量门禁

- `cargo fmt --all --check`、`clippy -D warnings`、`cargo test --workspace --all-targets --locked` 全绿；
- 兼容矩阵至少覆盖 1.2.1 / 1.3.0 / 1.4.0 / 1.5.0 客户端 × 1.4.0 / 1.5.0 服务端；
- 10 client 并发 `1000/1000`、`fail=0`；
- 20% 弱网 `20/20`、`reconnect: PASS`；
- ZAP baseline 0 High / 0 Medium；

## 10. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 没有第二台 relay | HA 无法生产验收 | 先在 staging 双机验收；生产保持 standalone；第二节点到位后再做 HA 上线 |
| 双 relay 双签发证书 | ACME 订单冲突、证书不一致 | 只有 primary 下单；secondary 只读；证书同步带 group HMAC；禁 secondary 配置 ACME 写权限 |
| 静态主备产生脑裂 | 双主同时改配置/证书 | V1.5 不做自动选主；bundle epoch + 配置 hash + 人工 runbook；角色错误拒绝启动 |
| TCP 主备被误解为“连接不中断” | 用户预期落差 | 文档明确：只保证新连接；在途连接不迁移；需要固定 VIP 时用外部 LB |
| Windows 签名证书缺失 | MSI/托盘发布阻塞 | H1 先交可安装 zip；签名 MSI 作为发布前门禁；无证书则 1.5.1 延期，不降低验证标准 |
| macOS 公证账号缺失 | macOS 包被 Gatekeeper 拦截 | 需 Apple Developer ID；无账号则 1.5.1 只交 ad-hoc 签名开发包，不宣称为正式包 |
| QUIC 控制面修复不达标 | `auto` 仍不可默认 | 保持 `transport = "tcp"`；G6 只交付修复或明确失败报告，不硬推默认 |
| 范围超 70 人日 | 质量被压缩 | 先保 G1–G5；H4 GUI 可后移 1.5.2，但不砍 HA；不把桌面塞进 1.5.0 |
| 共享证书目录不可用 | secondary 无法自动续期 | `cert_sync = push/pull` 之外保留 `meatus relay bundle` 手工同步路径 |

## 11. 发布与回滚策略

1. `1.5.0-rc.1` 只发 staging 双 relay，完成 HA 混沌和 24h soak 后再转正式；
2. `1.5.0` 生产先在单 relay standalone 升级，保留 1.4.0 镜像、`/data` 备份和旧容器；

### G3-03 TCP/UDP 主备接管（演练完成，2026-11-24）

- 运行时结论：G3-01/G3-02 已让每个成员各自持有控制会话、数据连接和影子注册；停掉 primary 不需要迁移客户端会话，secondary 的端口映射与转发链路仍在，因此新连接可直接进入 secondary。
- e2e 升级：同一双 relay 场景增加 TCP `echo` 与 UDP `udp-echo`；两个 relay 使用互不重叠的端口段，注册完成后先验证四路可达。停掉 relay-a 并等待服务退出后，断言 relay-a 的 TCP 端口已关闭，再用同一个 5 秒预算建立新 TCP 连接和 UDP 会话，均从 relay-b 成功回显。
- 在途连接：不做迁移；停止 primary 时已建立的连接允许失败，验收只看新 TCP 连接与新 UDP 会话。
- 端口语义（重要）：bundle 要求同组成员端口段严格不重叠，同一 proxy 在 relay-a / relay-b 上的公网端口通常不同。固定“同域名同端口”的 TCP/UDP 入口需要外部 LB/VIP 或双地址客户端；本版不引入全局端口分配器。
- 验证：`fmt --check`、`clippy -D warnings`、`cargo test --workspace --all-targets --locked` **275 passed / 0 failed / 1 ignored**。
- 未闭环：真实双主机、DNS 双 A 未验收；客户端 admin 热加 proxy 仍未跨成员补注册。

- 运行时：新增 `crates/meatus-server/src/relay_health.rs`，本节点按 `relay.health_interval_s` 主动探测 bundle 内其余成员；单次请求受 `relay.peer_timeout_s` 约束；探测结果写入 `Metrics`，`/healthz` 与 `/metrics` 共用同一快照。
- 端点前置：`health_bind` 不再只在 `cert_sync != off` 时监听；只要配置了 `[relay]` 就启动 peer 端点，`cert_sync = off` 时只提供健康查询，证书端点仍因缺少 `peer_auth` 返回 403。
- `/healthz`：保留 `status` / `uptime_s`，新增 `relay` 对象：`id/group/role/epoch/cert_sync/state/peers_up/peers_total/peers[]`；`state = healthy` 仅当所有 peer 可探测且 id、group、role、epoch 均与本地 bundle 一致，否则为 `degraded`；standalone 下 `relay = null`，`status` 仍为 `ok`。
- peer 明细：每个 peer 输出 `id/role/peer_addr/up/peer_epoch/latency_ms/last_checked_age_s/last_ok_age_s/last_error`；失败保留最近错误与对端 epoch，便于 G4-02 识别故障与配置漂移。
- metrics：新增 `meatus_relay_info{relay_id,group,role,epoch,cert_sync}`、`meatus_relay_epoch{relay_id}`、`meatus_relay_peer_up{relay_id,peer,role}`；`peer_up` 只在对端身份与 epoch 全部匹配时为 1。
- 配置：`[relay]` 新增 `health_interval_s`，默认 `5`，范围 `1..=300`；TOML/YAML 示例同步。
- e2e：`client_multi_home_registers_same_proxies_and_secondary_takes_over` 增加健康断言。双 relay 在线时 relay-a `/healthz` 报 `healthy`、`peers_up=1`，`/metrics` 含 `role="primary"`、`epoch="2"`、`peer_up=1`；停 relay-a 后 relay-b `/healthz` 转 `degraded`、`peer_up` 变 0，并保留失败原因。
- standalone 回归：`ten_proxies_and_metrics_endpoint` 增加断言，`/healthz` 的 `relay` 为 `null`，`/metrics` 不出现 `meatus_relay_info`。
- 验证：`fmt --check`、`clippy -D warnings`、`cargo test --workspace --all-targets --locked` **279 passed / 0 failed / 1 ignored**（ignored 仍为 SIGHUP 手动验收用例）。
- 信任边界：`/relay/v1/health` 目前是不鉴权的观测端点，只证明网络可达与身份字段一致，不能作为 G4-02 自动摘除的唯一授权依据；自动摘除应叠加签名探测、外部 LB 健康检查或管理面确认。真实双主机与 DNS 双 A 仍未验收。
