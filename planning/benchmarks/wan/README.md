# V1.4 公网端到端性能实测（E5-02 补充）

## 目的

验证 V1.4 的 QUIC / TCP 性能门禁不只在 loopback 成立：从本机经真实公网连接到生产服务器上的临时 1.4 服务端，用同一 echo 场景对比 TCP 与 QUIC，并用官方 1.3.0 做同参数 TCP A/B。

## 环境与拓扑

| 项 | 值 |
| --- | --- |
| 客户端 | macOS / arm64 / 8 CPU，公网出口 `153.3.163.91` |
| 服务端 | 腾讯云轻量 `43.173.105.47`，地域硅谷，Ubuntu / Linux 6.8 / 2 vCPU / 1.9GB |
| 链路 | 跨国公网，裸 TCP 握手 p50 约 300–320ms，抖动明显 |
| 服务端二进制 | 1.4 源码 release 构建（`meatus-1.4`）；修复前 sha256 `87b8e00d…`，E5-05 修复版 sha256 `cd5ffecb…`；1.3.0 官方 Linux musl，sha256 `94627dc0…` |
| 端口 | TCP 22000 控制面、TCP 22001 代理面、UDP 22000 QUIC；腾讯云防火墙仅放行 `153.3.163.91/32` |
| 线上容器 | `meatus-server:1.3.0` 全程未动；临时服务端独立目录 `/home/ubuntu/meatus-wan`，使用自签证书 |

> 公网 IP 是 NAT 后的 `10.4.0.14`，生产 80/443/7000 被线上容器占用，因此使用临时端口与独立进程，不触碰生产服务。

## 方法

- 工具：`scripts/bench-wan.py`。本机启动临时服务端（SSH）→ 本机启动 1.4 / 1.3 客户端 → 本机 echo → 通过公网代理端口压测。
- 场景：`duration=10s`，1s 预热不计入吞吐；默认 `concurrency=8`、`payload=4096`；扩容组 `concurrency=32`、`payload=16384`。
- 每轮前先测公网 TCP 握手（直连 22000）作为链路基线，再测 1 并发 × 64B × 5s 的空闲 RTT，最后测加载吞吐。
- 指标口径与 loopback 一致：双向字节 / 墙钟为吞吐，单次 echo 为 p50 / p99。
- 门禁沿用 `bench-gate.py`：QUIC 吞吐 ≥ TCP 2/3，QUIC P99 ≤ TCP 1.5×。

原始结果：同目录 `tcp-1.4-r*.json`、`quic-1.4-r*.json`、`tcp-1.3-r*.json`、`*-c32*.json`。

## 结果一：8 并发 × 4KB（4 轮）

| 配置 | 吞吐 Mbps（4 轮） | 均值 | p50 ms（4 轮） | p99 ms（4 轮） |
| --- | --- | --- | --- | --- |
| 1.4 TCP | 0.197 / 0.203 / 0.452 / 0.223 | **0.269** | 2548 / 2760 / 1214 / 2839 | 9960 / 6808 / 2619 / 5225 |
| 1.4 QUIC | 0.413 / 0.380 / 0.636 / 0.387 | **0.454** | 1361 / 1293 / 753 / 1287 | 2725 / 3688 / 1560 / 3941 |
| 1.3 TCP | 0.229 / 0.334 / 0.210 / 0.262 | **0.259** | 2666 / 1284 / 2767 / 1770 | 4466 / 5772 / 4562 / 5143 |

- QUIC / TCP 吞吐比：均值 **1.69×**（逐轮 2.10 / 1.87 / 1.41 / 1.74）。
- QUIC / TCP P99 比：均值 **0.48×**（逐轮 0.27 / 0.54 / 0.60 / 0.75）。
- 公网门禁：**通过**，且四轮全部满足吞吐 ≥2/3、P99 ≤1.5×。
- 1.3 与 1.4 TCP：均值 0.259 vs 0.269 Mbps，差异约 4%，落在链路抖动区间；p50 均值 1.3 更低（2122 vs 2340ms），不能据此判定 1.4 回退。

## 结果二：32 并发 × 16KB（扩容组）

| 配置 | 吞吐 Mbps | p50 ms | p99 ms | 备注 |
| --- | --- | --- | --- | --- |
| 1.4 QUIC r1 | 3.277 | 2831 | 8484 | 成功 |
| 1.4 QUIC r2 | 3.670 | 2417 | 7134 | 成功 |
| 1.4 TCP r1 | — | — | — | 32/32 worker 预热阶段被关闭，无结果 |
| 1.4 TCP r2 | 1.416 | 12269 | 21472 | 成功，但严重拥塞塌陷 |
| 1.4 TCP r3 | — | — | — | 32/32 worker 预热阶段被关闭，无结果 |

- QUIC 两次均成功，均值 **3.47 Mbps / p50 2.62s / p99 7.81s**。
- TCP 3 次中仅 1 次成功；成功轮吞吐 1.416 Mbps，p50 12.27s、p99 21.47s，相对 QUIC 吞吐 **0.41×**、p50 **4.7×**、p99 **2.8×**。
- TCP 失败轮客户端日志为 `yamux inbound stream failed: peer closed connection without sending TLS close_notify`，32 条 data stream 全部在预热阶段关闭；控制会话在首条流建立约 26s 后断开。此前 64 并发 × 64KB 也出现同类现象（控制会话约 46s 无 Pong 后断开）。
- 这是公网高 RTT / 丢包下 TCP 单连接多流（yamux）队头阻塞与心跳饥饿的表现；QUIC 的多流独立拥塞控制与传输层重传显著更稳。根因与修复见下节“结果三”。

## 结果三：E5-05 修复后公网复测

修复版服务端 sha256 `cd5ffecb8…`，客户端为同源码 macOS release；测试前重新放行 `153.3.163.91/32` 的 TCP 22000-22001 与 UDP 22000，测试后已删除临时规则并恢复原 5 条。

- 对照修复前：3 轮仅 1 轮成功（1.416 Mbps、p50 12.27s），另 2 轮 32 条流在预热阶段全部关闭。修复把成功率从 1/3 提升到 3/3，但没有消除单数据连接上的 yamux 队头阻塞。

### 32 并发 × 16KB TCP：默认 2 条 vs 4 条数据连接 A/B（E5-07，6 轮）

E5-06 后 p99 仍有 26–34s 长尾。先在服务端对 22000 端口做 `ss -tinm` 连续采样（140s 覆盖负载窗口）：负载中 `cwnd` 中位仅 9 MSS（约 12.6KB）、低至 4–7，`rtt` 300–380ms；同窗口 `nstat` 增量 `TcpRetransSegs 61`、`TcpExtTCPTimeouts 8`、`TcpExtTCPLostRetransmit 1`。`snd_wnd` 131072、`rcv_space` 14480 均未打满，说明瓶颈是丢包导致的 cwnd 塌陷 + RTO 退避，不是 yamux 窗口或接收缓冲；单连接在 300ms RTT 下只剩约 30–45KB/s。

- **吞吐与延迟**：QUIC 在 32×16KB 下稳定领先约 2.1×，p50 约为 TCP 的 30%，p99 约为 45%。这与 E5-02 的 QUIC 3.277 / 3.670 Mbps 旧结果一致，说明增益可复现。
- **失败模式**：`quic-fail-1` 为 32/32 worker 失败，客户端控制连接建立后约 69s 无 Pong（`no Pong for 68.988979041s`），被客户端判死后重连；服务端日志随后出现 yamux `unexpected eof` / `Connection reset by peer`。`quic-r5` 为 3/32 worker 单请求超过 60s 超时。两次都发生在数据面高负载窗口，控制面与数据面共享同一条 QUIC 连接（`max_concurrent_bidi_streams(1)`，上层 yamux 复用），存在控制帧被数据帧排队拖住的嫌疑，但本轮未做抓包/逐流计时，根因未钉死。
- **小包对照（8×4KB，单轮）**：QUIC 0.229 Mbps / p50 2364 / p99 7477；TCP×4 0.328 Mbps / p50 1786 / p99 7676。单轮 TCP 略优，但差异落在抖动区间，且与 E5-02 四轮 QUIC 均值 0.454 vs TCP 0.269 Mbps 相反；小包不作为决策主依据。
- **64 并发 × 16KB（单轮）**：QUIC 4.666 Mbps / p50 3991 / p99 9436；TCP×4 2.123 Mbps / p50 11536 / p99 22242。QUIC 吞吐 2.2×、p50 −65%、p99 −58%，并发越高优势越明显。
- **握手与空闲**：QUIC 握手 p50 326–413ms，TCP 318–440ms，基本持平；QUIC 空闲 p50 715–1574ms，TCP 738–1049ms，QUIC 未体现明显优势。
- 结论：**性能上 QUIC 值得作为弱网/高 BDP 的推荐传输，但当前 71% 的整轮成功率不足以在 1.4 直接改默认**。默认继续 `Tcp` + 4 条数据连接；QUIC 保持显式 opt-in，并在 1.5 优先修控制面饥饿（独立控制连接或原生 QUIC 多流）后再评估 `Auto`。

## 结论

1. **公网门禁成立**：8×4KB 四轮全部通过，QUIC 平均吞吐为 TCP 的 1.69×，P99 为 0.48×。
2. **公网 TCP 相对 1.3.0 无显著变化**：差异在 ±4% 与抖动区间内；loopback 上 24× 的提升来自消除 Nagle + 延迟 ACK 的 40ms 固定代价，在 300ms RTT 链路上被稀释，属于预期。
3. **QUIC 的价值在高并发才充分体现**：32×16KB 下 QUIC 稳定成功且吞吐 3.3–3.7 Mbps；TCP 出现 2/3 失败或 p50 12s 的拥塞塌陷，说明 V1.4 的多流 QUIC 路径是公网弱网场景的实际增益。
4. **TCP 高并发断连已在公网验证修复**：默认未启用连接池时数据流与控制心跳共用一条 TCP 发送队列；高 RTT 下数据帧排队超过服务端 25s 空闲阈值，整条隧道被关闭。修复后控制连接标记为 control-only、TCP 默认建立独立数据连接，服务端空闲阈值提升到 75s。公网 32×16KB 三轮 32/32 全部成功，控制会话均存活到测试主动结束。
5. **默认 2 条 TCP 数据连接（E5-06）成立**：10 轮交替 A/B 中，1 条连接 4/5 轮成功、p50 中位 17.6s，1 轮整轮超时；2 条连接 5/5 成功、p50 中位 10.0s、p99 中位 13.9s、吞吐中位 1.389 Mbps。两条连接把 32 条 yamux 流分散到两个独立 TCP 拥塞窗口，队头阻塞与失败风险明显下降。已把默认定值改为 2，未新增对外配置项；需要更多连接仍走 `[client.pool]`。
6. **默认 4 条 TCP 数据连接（E5-07）成立**：6 轮交替 A/B 中两版本均 32/32 全成功；4 条对比 2 条 p50 中位 14.2s → 4.2s、p99 20.0s → 11.8s、吞吐 1.363 → 2.176 Mbps。长尾根因是公网丢包下的 cwnd 塌陷与 RTO（cwnd 中位 9 MSS、300–380ms RTT），增加并行连接能把单窗口塌陷的影响摊薄，但不改变根因。
7. **长尾仍在**：4 条连接的 p99 单轮仍可达 13.6s；默认值解决的是典型延迟与整轮失败，不替代 BBR / QUIC 数据面等更彻底的方案。
8. **QUIC 数据面（E5-08）性能成立、稳定性未达标**：同窗 A/B 中 QUIC 吞吐为 TCP×4 的 2.12×，p50 −70%、p99 −55%，64 并发下扩大到 2.2×；但 7 次 QUIC 尝试有 2 次出现整轮或部分 worker 超时（控制面约 69s 无 Pong），整轮成功率 71%。因此 1.4 默认仍为 TCP×4，QUIC 作为显式 opt-in；把 QUIC 升为 `Auto` 默认前，必须先解决控制面与数据面共享单条 QUIC 连接导致的饥饿问题。

## 限制

- 单地域、单运营商、单时段采样；未覆盖跨洲多跳、移动网络与丢包注入。
- 服务端为 2C2G 轻量实例，CPU 与带宽上限低，绝对吞吐不代表产品上限。
- 临时自签证书 + 单客户端，未覆盖多客户端竞争与 ACL / 限速路径。
- 1.3.0 客户端版本号仍显示 `meatus 1.3.0`（1.4 未 bump），A/B 以二进制来源区分。

## 复现

```bash
python3 scripts/bench-wan.py \
  --server-bin meatus-1.4 --client-bin target/release/meatus \
  --transport quic --concurrency 8 --payload 4096 --duration 10 \
  --out planning/benchmarks/wan/quic-1.4-rN.json
```
