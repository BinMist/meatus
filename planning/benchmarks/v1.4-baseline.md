# V1.4 性能基线（E5-02）

## 场景

- 工具：`scripts/bench.py`，固定 echo 场景，TCP / QUIC 各跑一轮；`scripts/bench.sh` 串联并调用 `scripts/bench-gate.py`。
- 参数：`duration=5s`、`warmup=1s`、`concurrency=8`、`payload=4096`（默认门禁场景）；补充单流 `payload=65536` 观察窗口与拥塞控制影响。
- 指标：吞吐（双向字节 / 墙钟）、p50 / p99 单次往返、服务端进程 CPU、RSS。
- 干净环境：Linux 6.6.95 / x86_64 / 2 vCPU / 3.9GB（云主机），采样时 load average 0.1；release 构建，服务端与客户端同机 loopback。
- 历史环境：macOS 26.5 / arm64 / 8 CPU（BinSail mini），采样时 load average ≈ 13，仅作趋势参考。
- 复现：`cargo build --release -p meatus-cli --offline && bash scripts/bench.sh`；1.3.0 基线加 `MEATUS_130_BIN=<fixture>/meatus`。

## 关键修复

- Linux 首轮 TCP 仅 28–34 Mbps、p50 约 40ms，原因是服务端接受的控制连接未设 `TCP_NODELAY`，Nagle 与延迟 ACK 叠加；对公网代理连接同样补齐。
- 修复后 1.4 TCP 提升到 856–982 Mbps（1.3.0 同机基线仅 37.4 Mbps），QUIC 保持 601–718 Mbps，门禁转绿。
- `scripts/bench.py` 的回声服务端与压测客户端也显式设置 `TCP_NODELAY`，避免工具自身污染基线。

## 门禁结论

- `scripts/bench-gate.py` 按 2/3 与 1.5× 阈值实现，超阈值退出 1；CI `perf` job 直接调用 `scripts/bench.sh`，失败阻断。
- 干净 Linux 三轮全部通过；当前门禁已具备可重复的通过证据。
- 仍建议在 CI runner 保留 artifact，持续观察吞吐比下限（最低一轮 0.692，余量约 4%）。

## 复现

```bash
cargo build --release -p meatus-cli
bash scripts/bench.sh
```

`MEATUS_130_BIN=<fixture>/meatus` 可补 1.3.0 TCP 基线；原始 JSON 写入 `bench-results/`，不入库。
