# V1.4 性能基线（E5-02）

## 场景

- 工具：`scripts/bench.py`，固定 echo 场景，TCP / QUIC 各跑一轮；`scripts/bench.sh` 串联并调用 `scripts/bench-gate.py`。
- 参数：`duration=5s`、`warmup=1s`、`concurrency=8`、`payload=4096`（默认门禁场景）；补充单流 `payload=65536` 观察窗口与拥塞控制影响。
- 指标：吞吐（双向字节 / 墙钟）、p50 / p99 单次往返、服务端进程 CPU、RSS。
- 干净环境：Linux 6.6.95 / x86_64 / 2 vCPU / 3.9GB（云主机），采样时 load average 0.1；release 构建，服务端与客户端同机 loopback。
- 历史环境：macOS 26.5 / arm64 / 8 CPU（BinSail mini），采样时 load average ≈ 13，仅作趋势参考。
- 复现：`cargo build --release -p meatus-cli --offline && bash scripts/bench.sh`；1.3.0 基线加 `MEATUS_130_BIN=<fixture>/meatus`。

### TCP 高并发控制面饥饿修复（E5-05，本机 loopback）

- 根因确认：默认 `pool.enabled=false` 时只有控制 TLS 连接，32 路 data stream 与控制 Ping/Pong 共用同一 TCP 发送队列；高 RTT / 丢包下数据帧排队超过服务端 `IDLE_TIMEOUT=25s`，控制会话被判空闲并关闭，客户端看到全部流被关。
- 修复后本机 32 并发 × 16KB × 10s TCP 三轮：3.094 / 3.328 / 3.276 Gbps，p50 2.87 / 2.66 / 2.70 ms，p99 5.59 / 5.15 / 5.22 ms，32/32 worker 全部成功。
- 服务端日志确认 `data connection registered`，控制连接与数据连接分离；`meatus_client_connected` 只统计控制会话。
- 回归门禁：`scripts/bench-tcp-concurrency.sh` 默认 3 轮 32 并发 × 16KB × 10s，任一 worker 失败即退出非零；已接入 CI `perf` job。
- 公网复测（修复版 Linux sha256 `cd5ffecb…`，临时端口 22000/22001，测试后防火墙已恢复原 5 条、临时目录与进程已清理）：32 并发 × 16KB TCP 三轮均 32/32 成功，p50 25398 / 17304 / 25267 ms，p99 57452 / 22639 / 31507 ms；未再出现 `echo closed`，控制会话存活到测试主动结束。修复前同参数 3 轮仅 1 轮成功，另 2 轮在预热阶段全部断流。
- 公网常规路径 8 并发 × 4KB 一轮：0.256 Mbps / p50 1886 ms / p99 7134 ms，落在修复前 4 轮抖动区间，无回退。
- 残留：32 并发 p50 仍为 17–25s，单数据连接上的 yamux 队头阻塞仍在；后续按 `E5-06` 评估默认 TCP 多数据连接与流调度，不把本次稳定修复当作吞吐提升。

### 默认 TCP 2 条数据连接 A/B（E5-06，公有云 + loopback）

- 方案：未启用池且 TCP 时默认 `DEFAULT_TCP_DATA_CONNECTIONS = 2`；不新增配置项，`[client.pool]` 语义不变，QUIC 默认路径不变。
- 公网交替 10 轮（32×16KB×10s，同服务端 `cd5ffecb…`）：

| 数据连接 | 成功轮次 | worker 成功率 | p50 中位 | p99 中位 | 吞吐中位 |
| --- | --- | --- | --- | --- | --- |
| 1 条 | 4/5 | 149/160（93%） | 17556 ms | 28281 ms | 0.839 Mbps |
| 2 条 | 5/5 | 160/160（100%） | 9975 ms | 13880 ms | 1.389 Mbps |

- 1 条连接的第 4 轮出现 11/32 worker 等待 Echo 超时（客户端日志无 WARN/ERROR，1 条数据连接、46 条流被受理）；同一窗口的 2 条连接轮为 53 请求 / p50 9.98s。失败记录见 `planning/benchmarks/wan/tcp-1.4-e5-06-a4-failure.txt`。
- 本机 loopback 门禁：32 并发 × 16KB 三轮 32/32（4.18 / 5.02 / 5.17 Gbps，p50 1.45–1.71 ms，p99 5.76–10.17 ms）；64 并发 × 16KB 一轮 64/64（5.23 Gbps，p50 2.84 ms，p99 14.31 ms）。
- 测试：client 13 passed、core pool 10 passed、server tunnel 22 passed / 1 ignored。
- 结论：2 条连接把 32 条 yamux 流分散到两个 TCP 拥塞窗口，典型延迟降 43%、p99 降 51%、吞吐升 65%，并消除整轮失败；长尾仍在（单轮 p99 26–34s），需要更多并行连接时开启池。

## 关键修复

- Linux 首轮 TCP 仅 28–34 Mbps、p50 约 40ms，原因是服务端接受的控制连接未设 `TCP_NODELAY`，Nagle 与延迟 ACK 叠加；对公网代理连接同样补齐。
- 修复后 1.4 TCP 提升到 856–982 Mbps（1.3.0 同机基线仅 37.4 Mbps），QUIC 保持 601–718 Mbps，门禁转绿。
- `scripts/bench.py` 的回声服务端与压测客户端也显式设置 `TCP_NODELAY`，避免工具自身污染基线。

## 门禁结论

- `scripts/bench-gate.py` 按 2/3 与 1.5× 阈值实现，超阈值退出 1；CI `perf` job 直接调用 `scripts/bench.sh`，失败阻断。
- 干净 Linux 三轮全部通过；当前门禁已具备可重复的通过证据。
- 仍建议在 CI runner 保留 artifact，持续观察吞吐比下限（最低一轮 0.692，余量约 4%）。
