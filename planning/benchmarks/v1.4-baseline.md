# V1.4 性能基线（E5-02）

## 场景

- 工具：`scripts/bench.py`，固定 echo 场景，TCP / QUIC 各跑一轮；`scripts/bench.sh` 串联并调用 `scripts/bench-gate.py`。
- 参数：`duration=5s`、`warmup=1s`、`concurrency=8`、`payload=4096`（默认门禁场景）；补充单流 `payload=65536` 观察窗口与拥塞控制影响。
- 指标：吞吐（双向字节 / 墙钟）、p50 / p99 单次往返、服务端进程 CPU、RSS。
- 机器：macOS 26.5 / arm64 / 8 CPU（BinSail mini）。采样时宿主 load average ≈ 13（Vite 开发服务占用约 3 核），数据用于趋势与门禁机制验证，不作为干净基线。
- 复现：`cargo build --release -p meatus-cli --offline && bash scripts/bench.sh`；1.3.0 基线加 `MEATUS_130_BIN=<fixture>/meatus`。

1.3.0 TCP 基线未在宿主高负载时重跑；发布前需在 CI 干净 runner 或空闲机器补录。

## 门禁结论

- 吞吐：4KB × 8 为 TCP 的 0.49；64KB × 1 首次 0.69、复跑 0.48–0.51。宿主负载是显著变量，需干净环境复测。
- P99：4KB × 8 为 1.88× TCP；64KB × 1 为 1.71–2.4×。QUIC 用户态收包与 yamux 单流复用带来的额外往返在当前场景无法满足 1.5×。
- `scripts/bench-gate.py` 已按 2/3 与 1.5× 阈值实现，超阈值退出 1；CI `perf` job 直接调用 `scripts/bench.sh`，失败阻断。
- 当前门禁未转绿，属发布阻塞项；需在干净 Linux runner 复测后再决定优化传输路径或调整阈值口径。

## 后续选项

1. 在 CI Ubuntu runner（UDP GSO 可用）复测，若仍不达标再优化。
2. QUIC 数据面绕过 yamux 单流复用，改为原生多双向流；工作量大，但能同时改善吞吐与尾延迟。
3. 调整门禁统计口径：吞吐用聚合 goodput、P99 用批量流水场景；需产品确认。
